# Validation

Source: [How Anthropic enables self-service data analytics with Claude](https://claude.com/blog/how-anthropic-enables-self-service-data-analytics-with-claude)

How you find out which of the three failure modes is still leaking through.

## Offline evaluations

Two kinds, run continuously:
- **Dashboard-based evals** — auto-generated by Claude, human validated, covering common stakeholder questions.
- **Long-tail evals** — Claude generates plausible questions from business context (roadmaps, table docs) across the rest of the domain.
- Every stakeholder correction in a thread is harvested as a candidate eval.

Practices:
- **Anchor ground truth so it can't drift** — pin to a snapshot date, use a stable fact table, or grade the agent's *query* rather than its number. Wire into CI so dependency changes re-run affected evals.
- **Store results as telemetry, not test logs** — skill version, git SHA, model ID, per-assertion pass/fail, tokens, wall-clock, all in a warehouse table. Makes "did that change help?" a query, and surfaces slow regressions a single CI run won't catch.
- **Gate launches per domain** — a domain can't ship to stakeholders until its eval slice clears a threshold (started at ~90%). Forces doc fixes before users see failures.
- **Right-size the eval count** — calibrate against how well offline accuracy predicts online accuracy; diminishing returns past a few dozen per topic, and that ceiling drops with each new model generation.
- **Offline eval accuracy target ~100%** — every correct answer should hit the semantic layer if one exists. High offline accuracy ≠ no bugs, just no obvious gaps (assuming coverage is real).

## Ablation techniques

Hold the offline eval set fixed, vary one component, compare pass rates (~1 hour per run).

- **Design for null results.** Biggest finding: giving the agent raw grep access to the entire dashboard/transformation/notebook SQL corpus moved accuracy <1 point, even though it verifiably read the files and the right answer was present in the corpus ~80% of the time it got a question wrong. Access wasn't the bottleneck — *structure* (mapping question → entity) was. Redirected months of roadmap.
- **Ablate at PR granularity** — every meaningful skill edit gets a before/after run on the relevant eval slice, delta posted in the PR description.
- **Log what didn't work**, cheaply, so it isn't re-tried: stacking doc-refinement rounds past a point (3 consecutive net-negative iterations — docs got longer, not better); swapping the adversarial reviewer for a cheaper model (lost most accuracy gains, no real speedup).

## Online validation

- **Adversarial review** — a skill that aggressively challenges the final answer's assumptions: +6% accuracy, but +32% tokens and +72% latency.
- **Provenance footer** — every response states source tier (semantic layer › curated reference › raw table), data freshness, and model owner. Doesn't improve correctness, but tells the consumer how much to trust it (e.g. "raw table, freshness unknown" = verify before forwarding).
- **Data quality checks** — the right field can still hold wrong data; basic freshness/completeness/anomaly checks are standard hygiene here too.
- **Passive monitoring** — two continuous signals: % of queries resolved via the semantic layer, and % of responses receiving correction language ("wrong table," "missing the fraud filter"). Reviewed weekly with offline pass rate.
- **Active correction harvesting** — a scheduled agent scans stakeholder channels for correction language, drafts a one-line reference-doc fix, opens a PR to the domain owner. Deliberately boring (edit markdown, merge, auto-sync) to keep the cost of fixing low. Feeds back into the offline eval set.

**Unsolved**: the *silent* failure — wrong answer, looks plausible, used without objection. Mitigated (not solved) by the provenance footer, human sign-off on leadership-bound answers, and a standing per-domain KPI eval that sanity-checks against the blessed dashboard daily.
