Framework de 9 passos para agentes de analytics / coding com Claude

Baseado em: Anthropic — self-service data analytics PT-BR
O problema

NÃO É CODEGEN.
É CONTEXTO.

  • Analytics tem uma resposta certa, de uma fonte certa — sem forma determinística de provar acerto depois.
  • O gargalo real: mapear a pergunta do usuário para a entidade certa e atualizada no modelo de dados.
  • Resolvido isso, o SQL vira trivial.
Fonte: 01-failure-modes.md
3 modos de falha

AMBIGUIDADE

centenas de campos plausíveis, agente escolhe errado

OBSOLÊNCIA

schemas e docs mudam, conhecimento apodrece

RETRIEVAL

a info existe, mas o espaço de busca é grande demais

Todo o framework abaixo ataca só isso três

01 / 09
C

CANONIZAR OS DADOS

  • Um dataset canônico por conceito de negócio — deprecie os quase-duplicados.
  • Rollups/caches derivam do canônico, não vivem como alternativa.
  • Agente busca conceito → acha uma resposta governada, não 40.
Ataca: ambiguidade Fonte: 02-data-foundations.md
02 / 09
H

HIERARQUIZAR FONTES DE VERDADE

  1. 1. Semantic layer — sempre primeiro
  2. 2. Lineage / grafo de transformação
  3. 3. Corpus de queries — só destilado, nunca cru
  4. 4. Contexto de negócio — a camada mais negligenciada
Ataca: ambiguidade Fonte: 03-sources-of-truth.md
03 / 09
E

ENFORCE VIA CI / TOOLING / MANDATO

  • Tooling: agente roteado pro canônico primeiro.
  • CI: mudança que ignora o canônico falha o review.
  • Mandato: time downstream usa a camada governada ou justifica.
Ataca: obsolência Fonte: 02-data-foundations.md
04 / 09
A

ARQUITETAR SKILLS EM PARES

  • Sem skills: acurácia ≤ 21%. Com skills: > 95%.
  • Conhecimento: router fino → semantic layer ou ~30 refs do domínio.
  • Runbook: clarifica → busca → query → revisão adversarial.
Ataca: retrieval Fonte: 04-skills.md
05 / 09
T

TESTAR OFFLINE COM EVALS

  • Evals dashboard-based + long-tail + correções de stakeholder.
  • Ground truth ancorado (snapshot de data), resultado salvo como telemetria.
  • Gate de lançamento por domínio: threshold antes de liberar (~90%+).
Ataca: todas — detecção Fonte: 05-validation.md
06 / 09
C

COMPARAR VIA ABLAÇÃO

  • Uma variável por vez, eval set fixo.
  • Desenhe pra resultado nulo: acesso bruto a milhares de SQLs moveu acurácia <1pt — o gargalo era estrutura, não acesso.
  • Registre o que não funcionou. É barato e evita repetir o experimento.
Ataca: todas — isolamento de causa Fonte: 05-validation.md
07 / 09
O

OBSERVAR EM PRODUÇÃO

  • Revisão adversarial: +6% acurácia / +32% tokens / +72% latência.
  • Rodapé de proveniência em toda resposta: fonte, freshness, dono.
  • Falha silenciosa ainda sem solução robusta — mitigue, não confie.
Ataca: falha silenciosa Fonte: 05-validation.md
08 / 09
D

DOCUMENTAR COMO CÓDIGO

  • Sem manutenção ativa: acurácia caiu de ~95% pra ~65% em 1 mês.
  • Skill markdown no mesmo repo do modelo — mesmo PR atualiza os dois.
  • Hook de review sinaliza modelo mudado sem skill atualizada.
Ataca: obsolência Fonte: 04-skills.md
09 / 09
E

EVOLUIR COM CORREÇÃO ATIVA

  • Agente varre canais, detecta correção, abre PR de doc pro dono do domínio.
  • Caminho deliberadamente chato: editar markdown → merge → auto-sync.
  • Toda correção realimenta o passo 5 (evals). Loop fechado.
Ataca: todas — loop fechado Fonte: 05-validation.md
Começar

MÍNIMO VIÁVEL

  • Um punhado de datasets canônicos — passo 1
  • Dezenas de evals offline — passo 5
  • Uma skill de conhecimento fina — passo 4
  • Depois: enforcement, ablação, observabilidade, correção ativa
